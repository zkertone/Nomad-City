# 城市移动执行链路 · 2026-10-18

本模块实现一次已授权的城市移动：支付 3 源石 → 沿选定单航道移动城市并清除对手影响力 → 仅未探索目标揭牌/等待事件选择 → 在目标点独立放置影响力。已探索目标不重抽、不重发事件奖励。

依旧由可信调用方授予一次行动机会，完整回合/角色/主要行动额度校验尚未实现。城市移动 complete 仅结束这一次主要行动的执行，不自动推进玩家、跳过快速行动或进入采集阶段。

## 已确认规则与实现

重新读取最新源码、DevLog、Accepted ADR-0001 和探索说明，视觉核对基础规则书 p06–07、p10–13，沿用已经核验的地图、人数红区规则和用户确认牌效，没有使用企业扩展或《感染者》。

| 事项 | 规则来源及行为 |
| --- | --- |
| 支付 | p06 城市移动：先完整支付 3 源石，不使用未来事件奖励垫付，不支付金券路费 |
| 单航道连接 | p06 及批准 Board 模型：实际源点和不同目标须共同属于选定航道；三/四端航道保持一个身份 |
| 目标 | p06–07：目标不能有其他城市；资源点红区限制按 p12/p23 的四人 4、三人 5、两人 6 回合开放 |
| 清除 | p07：所用航道槽及目标点槽内，全部对手影响力移回各自供应；保留本人影响力 |
| 清除范围 | 不包括源节点、分叉的其他端点或未选择的另一条航道；城市移动不会拆分航道 |
| 必要事件 | p07：目标没有资源标记才抽对应事件；先移动和清除，再调用已实现的事件结算核心 |
| 末尾放置 | p07/p13：事件后另在目标点放置；按更新后的空槽和本人库存判断，不能由事件额外放置替代 |
| 尽量执行 | p13：没有真实标记/合法槽则跳过放置，保留已经支付的费用、移动/清除和事件奖励 |

普通城市移动不额外获得 B-01 的初始入场奖励，也不因为红牌资源标记 ×2 而双倍发即时奖励。这里不实现角色或城市样式对费用/行动的特殊改写。

## 接口与职责

主要源码位于 `packages/game-core/src/game/city-move.ts` 和 `city-move-invariants.ts`；从根包和 `/game` 导出。

- `openCityMoveWindow(state, definition, {actorId, roundNumber, expectedVersion, deckOrder?})`：可信服务端授予一次城市移动，复用和探索一致的准备检查；首次牌堆准备规则相同，之后不重置或重洗。
- `getCityMoveOptions(state, definition, actorId)`：返回可用 `{nodeId, routeId}`；不同航道连接同一对节点时保留多个选项，不替玩家猜选。费用不足、错误玩家或不在 ready 阶段返回空列表。
- `applyCityMoveCommand(state, definition, {authenticatedPlayerId}, payload)`：验证身份/对局/版本/阶段并执行纯状态转换。输入不改动，结果解析校验后深度冻结。
- `getPendingCityMoveChoiceRequirements`、`getCityMoveFinalSlotIds`：只提供当前事件/目标放置选项，不授权额外行动。

玩家请求仅接受以下字段：

| type | 除 gameId / expectedVersion 外的字段 |
| --- | --- |
| move-city | nodeId、routeId |
| choose-city-move-event | choice：choiceId、必要时的 costDecision / influenceSlotId |
| place-city-move-influence | slotId |

源节点从当前城市推导；资源费用、清除范围、抽牌和奖励由服务器决定。不能在请求中提交源点、费用、待清除槽列表、牌号、身份、回合或路费收款人；也不接受探索的多段 path。

## 顺序与恢复

移动请求成功后，3 源石已扣除、城市已到目标、对手标记已归还。目标未探索时，节点/路线/新事件及待选阶段一起保存；恢复后只处理当前选择，不重新扣费、移动、清除或揭牌。错误选项/条件费用不足不会回滚此前已完成的移动，玩家继续提交合法选择。

已探索目标的 `cardId` / `resolvedChoiceId` 为 null，直接进入目标影响力阶段；其资源标记原样保留，不重触发原牌。目标两槽均为本人影响力时，保留这些标记并自动结束，不为了放新标记删除旧标记。

事件结算时看到的是清除后的棋盘和新城市位置，因此 Y08 可以选择刚清空的关联航道槽，Y05/R06 可以在有自己城市的目标点放置。事件用完最后标记后，末尾放置跳过；被归还的对手标记仍属于对手，不会变成本人的供给。

## 与探索共存

内部 `action-window.ts` 抽取两类行动共用的窗口准备、版本、人数牌堆和回合不倒退检查；`action-invariants.ts` 统一玩家顺序、所有城市已在探索点、剩余牌精确集合等检查。目标点末尾空槽也复用同一个纯查询。没有替换原有 Board/事件/库存结构或引入通用 force/ignoreRules。

| 格式 | 支持的实际阶段 | 兼容处理 |
| --- | --- | --- |
| 1.0.0 | 入场前 | 保留原解析 |
| 1.1.0 | 入场进度 | 保留原解析与明确结束要求 |
| 1.2.0 | 原探索 | 原探索行为和导出继续支持 |
| 1.3.0 | 城市移动，或之后的探索 | 每次只保存当前一种行动进度；保存同一牌堆和 playerOrder |

首次授予城市移动明确转为 1.3.0。之后再授予探索时仍保持 1.3.0，不降回 1.2.0，不复活旧行动记录，也不从头准备牌堆。所有阶段共用唯一 `stateVersion` 与权威棋盘、玩家和供应字段。没有自动存档迁移、第二套位置事实或新的项目发布版本。

完整 GameState 校验除原逐枚库存守恒、目录和地图引用外，还检查当前城市确实在移动目标、源/目标属于选定单航道、目标红区已开放、清除范围内没有残留对手、事件/选项/阶段一致。该校验不能证明完整历史或可信服务端授予机会是否合法，不能据此接受客户端整份状态。

## 未完成的边界

`openCityMoveWindow` 和 `openExplorationWindow` 都必须由未来回合模块确认角色阶段、顺时针顺序、主要行动额度及全局回合后调用，不能作为玩家端点。当前没有这套调度、认证服务、数据库 CAS/事务或跨进程幂等。隐藏牌序不可直接广播；公开投影、UI、联机和部署均未实现。

真实测试见 [验证记录](testing/city-move-validation-2026-10-18.md)。下一步可实现部署与调度，再整合主要行动的统一授权；角色和城市样式特殊效果仍需已确认资料才能实现。
